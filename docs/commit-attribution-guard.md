# Commit attribution guard

Tracked by [#66](https://github.com/im-tnyx/Tio-Ledger/issues/66). `AGENTS.md` remains the normative policy.

## What it enforces

- A `pull_request_target` runner executes trusted `main` code at the PR base SHA; the PR head is fetched as Git objects only, never checked out or executed.
- `scripts/check_commit_attribution.sh` inspects every commit in `base..head`, parses Git trailers, and checks common free-form AI-credit footers.
- It rejects recognized provider/model `Co-Authored-By` and similar AI signatures or self-credit (including versioned GPT/Gemini models, Cursor and standalone `AI-assisted` / `Generated by AI` footers). An employer's AI-provider domain by itself is **not** a prohibited bot identity: legitimate human co-authors and sign-offs, including employees of model companies, are allowed. Known bot automation mailboxes on such domains are still rejected. Ordinary tool discussion is allowed. Unknown or deliberately ambiguous AI identities cannot be detected perfectly from arbitrary names.
- Gemini matching is limited to rejecting prohibited model-attribution strings such as `Gemini 2.5 Pro`; no Gemini service, API, dependency, or code assistant is enabled by this guard. Free-form lines with structured human `Name <email>` credits use precise identity rules, and ordinary prose such as `AI-assisted transaction import still requires explicit user confirmation.` is not treated as a credit footer.
- Exit status: `0` clean or exact owner-approved PR exception, `1` prohibited credit, `2` technical failure. Technical failures are never exempted.
- The Actions job `Attribution guard runner` publishes a different required Check Run named `Commit attribution guard` using a dedicated GitHub App. The check must be pinned to that App ID.

## Required owner/admin activation

1. Install the existing `Tio Attribution Guard` GitHub App on `im-tnyx/Tio-Ledger`, or register a new dedicated Checks-only App. Grant `Checks: Read and write` plus `Metadata: Read`, without unrelated permissions. Keep the installation scoped to this repository.
2. Create Actions environment `attribution-guard-trusted` and restrict deployment branches to `main` only. Save `ATTRIBUTION_GUARD_APP_PRIVATE_KEY` as an environment secret (the PEM private key) and `ATTRIBUTION_GUARD_APP_CLIENT_ID` as an environment variable. Never store the key in Git.
3. The owner has already activated a `main` ruleset (ID `25645516`) requiring the existing KMP, SQLDelight and attribution **fixture** checks. **These checks are not the App-owned scanner.** Review and merge this guard PR only with explicit owner authorization and a clean, human-checked final merge message (see below).
4. Once the workflow is on `main`, verify that a clean disposable PR publishes a `Commit attribution guard` Check Run from the dedicated App on the exact PR head SHA. Verify a prohibited-AI-attribution PR fails and cannot merge once the App-owned check becomes required. Never merge a deliberately bad test PR.
5. Add `Commit attribution guard` as a required status check in the `main` ruleset **pinned to the GitHub App source**, not to `github-actions`. Then verify a remediated PR succeeds. Record App ID, links and complete live results in #66. Do not mark fully enforced until these steps succeed.

## Final merge-message gap and protection

A passing `Commit attribution guard` checks the PR's existing `base..head` commits. GitHub **squash** and **merge-commit** methods can create a new message at merge time *after* those checks. **The App check cannot inspect a not-yet-created commit or guarantee a clean final squash message.** This is distinct from PR-commit checking.

- **Before any owner-approved merge:** the owner must inspect the complete final commit subject/body/trailers in the GitHub merge confirmation UI or use an explicitly clean merge message. Never accept an AI provider footer from generated defaults. If a prohibited footer is present, remove it before confirming. This is a **human process gate**, not an automatic server-side guarantee.
- **For a stronger future automated boundary:** have the repository owner evaluate limiting `main` to a rebase-based merge method, after considering GitHub rebase SHA/signature tradeoffs and the repository's existing squash workflow. GitHub rebase merges do not introduce a separate editable squash/merge commit message. **No merge methods are changed by this PR.**
- If `Restrict commit metadata` is available under the repository's GitHub plan, evaluate `Must not match a given regex pattern` restrictions against the *resulting* `main` commit message, with explicit human-attribution false-positive fixtures and a disposable merge validation. Availability is plan-dependent. **This PR does not create such a rule.**
- `.github/workflows/commit-attribution-main-audit.yml` also audits **newly reachable `main` commits after a push**, including merge/squash messages. An audit failure calls attention to an already-landed bad commit; **it cannot prevent or undo that merge**. Do not add this post-merge audit as the only required *pre-merge* guard.

For full prevention, prefer a validated repository-enforced final-commit metadata restriction or reviewed merge method, in addition to the PR App check. Until then, describe coverage as PR commit validation plus explicit owner merge-message review and post-merge detection.

## Developer remediation

Run `bash scripts/check_commit_attribution_test.sh` and inspect the checker log to find the offending feature-branch commit. The fixture suite includes multi-commit scans where an earlier commit is prohibited even if the last commit is clean. Remove any prohibited trailer/footer from that feature branch only. Published feature-branch rewrites need explicit owner approval and `git push --force-with-lease`; never rewrite `main`. Supply explicit clean squash-merge subject/body.

An exceptional owner-approved PR may be authorized through the repository Actions variable `AI_ATTRIBUTION_EXCEPTION_PR` set to its exact numeric PR ID. Clear it after that PR. An exception never suppresses technical failures.

Historical cleanup is outside this work and remains in [#83](https://github.com/im-tnyx/Tio-Ledger/issues/83). No Kotlin, KMP, SQLDelight, finance, ledger or UI logic changes are required.
